# نقل تكيّة إلى MariaDB 10.11 على Hostinger

## الحالة الحالية — ليست نسخة تشغيل مكتملة لـ MariaDB

تم تجهيز مُصدّر للهيكل والبيانات المختارة، وموصل MariaDB أصلي منفصل،
وتعريفات Drizzle أصلية لكل الجداول في `lib/db/src/mariadb/schema/`.
توجد أيضاً نماذج تطبيق أصلية تحفظ أسماء الخصائص وأنواع JSON والتحقق من
مصفوفات النصوص في `lib/db/src/mariadb/application-schema/`، ويمكن إعادة
توليدها بالأمر `pnpm --filter @workspace/scripts run generate:mariadb-contracts`.
**الخادم الرئيسي ما زال يستخدم PostgreSQL. لا تضع عنوان MySQL داخل
`DATABASE_URL` ثم تنشر التطبيق الحالي؛ ذلك لا يحوّل الاستعلامات إلى MySQL.**

لم تُحذف أو تُعدّل قاعدة PostgreSQL أثناء التصدير. لا توجد عملية استيراد تلقائية
عند تشغيل التطبيق، ولا استعادة لبيانات تجريبية أو نسخة إنتاج سابقة.

## نطاق التصدير المعتمد

- هيكل جميع جداول قاعدة التطوير الفعلية، بما فيها الجداول القديمة التي قد لا
  تكون ممثلة بالكامل في تعريفات Drizzle الحالية.
- بيانات `site_settings` فقط، مع استبعاد مفاتيح كلمات المرور والمفاتيح السرية.
- حساب المدير النشط `admin` فقط، بمعرّفه وتجزئة كلمة المرور الحالية وصلاحياته.
- لا تُنقل حسابات الملاك أو الموظفين الآخرين، الحجوزات، الطلبات، المبيعات،
  المصروفات، الجلسات، رموز الاستعادة أو المعاملات المالية.
- إعدادات SMTP المنفصلة ليست ضمن التصدير. الصور والملفات المرفوعة ليست بيانات SQL.

## إنشاء الملفات

من جذر المشروع:

```sh
pnpm --filter @workspace/scripts run export:mariadb
```

يُنتج مجلداً مؤرخاً داخل `.local/mariadb-exports/`:

| الملف | المحتوى |
|---|---|
| `schema.sql` | الجداول والفهارس والقيود والعلاقات |
| `seed.sql` | الإعدادات وحساب المدير فقط |
| `manifest.json` | نطاق التصدير، قرارات تحويل الأنواع وبصمات SHA-256 |
| `verification.json` | نتيجة التحقق، يُنشأ بعد الاستيراد والاختبار |

**الملفات خاصة:** يتضمن Seed تجزئة كلمة مرور المدير وبيانات التواصل. لا ترفعه
إلى Git أو `public_html` أو أي مسار تنزيل عام. `.local` مستثنى من Git والنشر
وممنوع بواسطة خوادم معاينة Vite الحالية. احتفظ بنسخة خاصة ثم احذف ملفات
الاستيراد المؤقتة من الاستضافة بعد الانتهاء.

المُصدّر يستخدم معاملة PostgreSQL للقراءة فقط بلقطة متسقة. يتوقف عند نوع أو
تعبير غير مدعوم، ولا يحذف القيود بصمت. لا يحتوي SQL الناتج أوامر حذف الجداول
أو تفريغها ولا يتجاهل الجداول الموجودة؛ الاستيراد لقاعدة جديدة فارغة فقط.

## قرارات توافق يجب مراجعتها قبل اعتماد التشغيل

- الترميز `utf8mb4` مع ترتيب `utf8mb4_bin` للحفاظ على تمييز المفاتيح بين
  الحروف الكبيرة والصغيرة كما في PostgreSQL.
- الحقول النصية المفهرسة أو المرتبطة بمفاتيح خارجية أصبحت `VARCHAR(191)`
  لتوافق حدود مفاتيح InnoDB؛ بقية النصوص `LONGTEXT`. توجد القائمة الكاملة
  للحقول ذات الحد الجديد في Manifest، ويُرفض Seed إذا تجاوز هذا الحد.
  لا تُفسّر هذا على أنه إثبات ملاءمة الحد لجميع الاستخدامات المستقبلية.
- المبالغ `DECIMAL` وليست أرقام فاصلة عائمة. الموصل لا يحوّل DECIMAL إلى Number
  تلقائياً، لتجنب فقدان دقة الحسابات.
- `timestamptz` يتحول إلى `DATETIME(6)` بتوقيت UTC، مع إبقاء عرض توقيت السعودية
  في التطبيق. لا تحفظ DATETIME بتوقيت الخادم المحلي.
- مصفوفات النصوص تتحول إلى JSON مع قيد يفرض كونها مصفوفة.
- فهارس PostgreSQL الفريدة الشرطية تتحول إلى أعمدة مولدة قابلة لـ NULL؛ لا
  يُحذف شرط التفرد. تبقى المفاتيح الخارجية وقيود الحسابات محمولة في SQL.
- تعريفات Drizzle الجديدة منفصلة عن التعريفات التي يستعملها الخادم حالياً.
  إعداد MySQL الأصلي هو `lib/db/drizzle.mariadb.config.ts`، ويستعمل
  `MARIADB_DATABASE_URL` فقط. لا تشغل `drizzle push` على قاعدة مستعملة،
  ولا تستخدم إعداد PostgreSQL الحالي مع MariaDB.
- يمكن إعادة توليد التعريفات الأصلية يدوياً من لقطة هيكل PostgreSQL:

  ```sh
  pnpm --filter @workspace/scripts run generate:mariadb-schema
  ```

  لا تعمل هذه الخطوة تلقائياً عند التشغيل أو النشر. SQL المصدّر هو ملف
  الاستيراد الذي تم التحقق منه؛ إنشاء تعريفات أصلية ليس تحويلًا لاستعلامات API.

## الاستيراد والتحقق

1. أنشئ قاعدة MariaDB **جديدة وفارغة** من hPanel، واختر UTF-8 الكامل.
2. استورد `schema.sql` ثم `seed.sql` عبر phpMyAdmin. إذا ظهر خطأ، توقف ولا
   تستخدم خيار تجاهل الأخطاء أو إعادة الاستيراد فوق قاعدة مستخدمة.
   استخدم `utf8mb4` لاتصال الاستيراد أيضاً، لا ترميز `utf8` القديم؛ تتضمن
   بعض القيم الافتراضية رموزاً تتطلب أربعة بايتات.
   قبل استعمال نماذج التطبيق الجديدة، طبّق أيضاً الترحيل الإضافي
   `lib/db/src/mariadb/001-application-contract.sql` على القاعدة الجديدة.
   يضيف حقلاً اختيارياً موجوداً في نموذج التطبيق لكنه غائب عن كتالوج المصدر
   القديم. هذا الملف **ليس مضمناً في ZIP السابق** ولا يجعل ذلك ZIP حزمة تطبيق
   نهائية. لا تعِد تطبيق ALTER بعد نجاحه.
3. خزّن اتصالها في أسرار البيئة باسم `MARIADB_DATABASE_URL` وبصيغة اتصال
   `mysql://`، دون وضع كلمة المرور في الكود أو المحادثة أو سطر الأوامر.
4. الموصل المنفصل متاح من `@workspace/db/mariadb`. يرفض غياب الاتصال ولا
   يرجع إلى PostgreSQL بصمت؛ `verifyTarget()` يتحقق من MariaDB 10.11.
5. من بيئة مخوّلة بالوصول إلى القاعدتين:

   ```sh
   pnpm --filter @workspace/scripts run verify:mariadb /مسار/مجلد/التصدير
   ```

   يتحقق من عدد الجداول، فراغ كل الجداول غير المشمولة، سلامة حساب المدير
   وتجزئة كلمة مروره، تطابق نصوص الإعدادات، العربية والرموز، العلاقات
   ونجاح الاتصال الأصلي من Drizzle. لا يطبع بيانات الحساب أو التجزئة.

**هذا ليس اختبار تسجيل دخول للمنصة بعد تحويلها**؛ لا يزال نقل استعلامات
الخادم مطلوباً قبل تشغيل المنصة على القاعدة الجديدة.

### طبقة الحفظ والأرصدة الأصلية

تتوفر `insertAndRead` و`updateAndRead` و`deleteAndRead` من
`@workspace/db/mariadb/mutations` كبدائل أصلية لاسترجاع السجلات بعد الحفظ.
تحتاج إلى `MariaDbTransaction` من الطبقة الجديدة، ولا تعمل كبديل مباشر على
مسبح PostgreSQL الحالي. التحديث يقفل الصفوف ويعيد قراءتها بمعرّفاتها الأصلية
حتى لو تغيّر شرط الفلترة أثناء الحفظ. الإدراج لا يستنتج نطاقاً متتالياً
لمعرّفات الإدراج الجماعي.

تتوفر محفظة أصلية من `@workspace/db/mariadb/wallet` تحفظ ارتباط هوية المستخدم
بحساب المالك، وتتحقق من تطابق إعادة العملية، وتمنع الصرف المزدوج والاسترداد
المكرر داخل معاملات MariaDB. **هذه الطبقة ليست موصولة بعد بجميع مسارات
الاشتراكات والدفع والاسترداد الحالية، ولا يثبت اختبارها سلامة تلك المسارات.**

أزيل اعتماد البحث العام للخدمات على `UNNEST` وفرز PostgreSQL العشوائي؛ تبقى
مطابقة المدينة والتغطية وترتيب النتائج داخل الخادم مع الحفاظ على عزل
الملاك النشطين. هذه خطوة تحويل فعلية، وليست دليلاً على زوال بقية اعتماد الخادم.

## ما بقي قبل اعتماد نقل المنصة بالكامل

1. ربط الخادم بتعريفات Drizzle الجديدة وتحويل الاستعلامات فعلياً إلى MySQL/MariaDB: عمليات
   `returning` والتعارضات، المعاملات، نتائج `execute`، الاستعلامات الخام،
   JSON والمصفوفات، فرز القيم الفارغة والتحويلات النوعية.
2. إعادة تصميم أقفال PostgreSQL الاستشارية بأقفال معاملات InnoDB المناسبة،
   تم استبدال الاستدعاءات في مسارات التطبيق بأقفال صفوف مشتركة. يبقى ربط
   جميع المعاملات بمحرك MariaDB الأصلي بعزل READ COMMITTED، والتحقق من
   السعة والحجوزات والاشتراكات والاستردادات وتسلسل أرقام الحجوزات بعد ذلك.
3. تعديل واختبار تعريفات الجلسات واستعادة كلمات المرور وعمليات المدير والمالك،
   والتأكد من بقاء الفواصل المالية والتأمين دون تكرار.
4. استبدال اعتماد تخزين الملفات على Replit بموفر قابل للعمل على Hostinger،
   ونقل الشعار والصور والفيديو والملفات الخاصة مع صلاحياتها. مجرد نقل مساراتها
   في `site_settings` لا ينقل ملفاتها.
5. تجهيز تشغيل Express مع الواجهة على Hostinger، دون الاعتماد على الموجه
   الداخلي لتطبيقات Replit، والتحقق من OAuth وSMTP والمهام الدورية وFFmpeg.
6. اختبار التسجيل والدخول والحجز والدفع والتقارير على MariaDB قبل ربط النطاق.

## مراجعة تشغيل Express والأقفال

تمت إضافة نقطة تشغيل منفصلة `artifacts/api-server/src/hostinger.ts`.
**هذه ليست نقطة تشغيل قابلة للإطلاق حالياً:** تتحقق قبل تحميل المسارات
والمهام من أن محرك التطبيق نفسه أصبح MariaDB، وترفض التشغيل ما دام الخادم
الرئيسي PostgreSQL. تغيير متغير البيئة لا يتجاوز هذا الشرط، ولا يجب تغيير
إعلان قدرة المحرك لمجرد تجاوز الحماية.

- عند اكتمال التحويل، يدعم `FRONTEND_DIST_DIR` تقديم React و`/api` من خدمة
  Express واحدة دون موجه Replit. لا تتحول أخطاء API أو الصور المفقودة إلى HTML.
- يحظر المقدم الملفات المخفية، ويعطّل كاش صفحة HTML، ويحتفظ بالكاش الطويل
  لأصول البناء ذات البصمة فقط. لا تضع أسراراً أو SQL أو روابط رمزية لملفات
  خاصة داخل مجلد الواجهة، حتى لو كان اسمها غير مخفي.
- التشغيل يتطلب `NODE_ENV=production`، منفذ `PORT` صحيحاً، اتصال
  `MARIADB_DATABASE_URL`، سر جلسة آمن، وتعطيل التهيئة التلقائية.
- فحص المصدر متاح بالأمر:

  ```sh
  pnpm --filter @workspace/scripts run audit:hostinger
  ```

  يُنشئ تقريراً خاصاً داخل `.local/hostinger-reports/` ويعيد رمز فشل عند
  العثور على اعتمادات مانعة. هذا جرد بنيوي، وليس مراجعة دلالية كاملة لـ SQL.
  تُستثنى ملفات الاختبار والـ fixtures وأوامر الصيانة؛ لا تشغّلها على MariaDB
  قبل تحويلها بصورة مستقلة.
- الأمر `pnpm --filter @workspace/api-server run build:hostinger` يشغّل هذا
  الفحص **قبل البناء**. نجاح الفحص مستقبلاً لا يغني عن اختبارات المسارات
  الحرجة والتخزين. المخرجات المرحلية ليست ZIP نهائياً معتمداً للرفع.

### بديل الأقفال الأصلي

أضيفت `withMariaDbTransaction` من `@workspace/db/mariadb/transaction` كطبقة
معاملات أصلية مستقلة. تستعمل صفوف InnoDB ضمن ٤٠٩٦ خانة قفل ثابتة،
تُختار بهويات SHA-256 وتُقفل بترتيب ثابت، ضمن اتصال
ومعاملة واحدة، وليس `GET_LOCK`. تحتاج إلى إنشاء جدول الأقفال قبل استقبال
الطلبات، باستخدام ترحيل منفصل؛ لا يوجد DDL أو تعديل
هيكل تلقائي داخل المعاملة.

- استُبدلت استدعاءات الأقفال الاستشارية في مسارات التطبيق بدالة
  `lockResource` من `@workspace/db/transaction-lock`؛ هذه SQL واحدة تعمل
  على PostgreSQL وMariaDB. هذا لا يحوّل بقية استعلامات تلك المسارات تلقائياً.
- التصادم بين الموارد في خانة قفل واحدة يضيف انتظاراً فقط ولا يضعف الحماية.
- الأقفال الحالية والطبقة الأصلية تتشاركان هويات الموارد والجدول التقني نفسه.
- أقفال الصفوف تنتهي مع `COMMIT/ROLLBACK`. لا تحذف صفوف الأقفال أثناء وجود
  عمليات نشطة. الجدول ثابت الحجم ولا يحتاج تنظيفاً دورياً.
- العزل `READ COMMITTED` لتجنب قراءة لقطة قديمة بعد انتظار قفل.
- لا توجد إعادة محاولة تلقائية للمعاملة أو الدفع. فشل تأكيد COMMIT ذي
  النتيجة المجهولة يتطلب المصالحة، ويدمر الاتصال بدلاً من إعادته للمسبح.
- لا تنفذ أوامر DDL أو COMMIT أو اتصالاً خارجياً داخل callback، ولا تحتفظ
  باتصال المعاملة لاستخدام لاحق.

تم اختبار التزامن والتراجع والسعة على MariaDB 10.11 محلي مستقل، دون استعمال
بيانات المنصة. **هذا اختبار للطبقة الجديدة، وليس اختباراً لعمليات المنصة
المالية بعد نقلها**؛ لا تزال استعلامات PostgreSQL الأخرى في الخادم الحالي.
استعملت الاختبارات محركاً مؤقتاً باتصال socket محلي فقط، دون نظام صلاحيات
إنتاج؛ لا يُعد نجاحها اختباراً لمستخدم قاعدة Hostinger أو صلاحياته أو TLS.

أُضيف الجدول التقني فقط إلى قاعدة التطوير الحالية، وتم التحقق من الأقفال
بموصل الخادم الحالي دون تغيير بيانات الأعمال. عند النقل إلى Hostinger،
أنشئ ملفه بالأمر `pnpm --filter @workspace/scripts run export:mariadb-locks`
واستورد `.local/mariadb-runtime/002-transaction-mutex.sql` قبل تشغيل الطلبات.
يعيد ملء الخانات التقنية فقط دون حذف أو تجاهل أخطاء بيانات الأعمال.
قد يحتوي تصدير جديد على هيكل الجدول فارغاً؛ الملف الإضافي يتعامل مع وجوده.

يمكن للدالة إنشاء خانة تقنية مفقودة داخل المعاملة باستخدام SAVEPOINT
واستدراك تعارض المفتاح فقط، دون إنشاء جداول أو إعادة محاولة عملية مالية.
تجهيز الخانات مسبقاً إلزامي عند إطلاق MariaDB لتجنب تنازع إنشاء الأقفال.
عند التحويل، **أوقف جميع عمليات الكتابة بالنسخة القديمة أولاً**؛ لا تُشغّل
نسخة تعتمد الأقفال الاستشارية ونسخة تعتمد أقفال الصفوف على القاعدة نفسها.

## استضافة Hostinger

يدعم توثيق Hostinger الحالي تطبيقات Node.js وExpress على Business Web Hosting،
لكن يجب إنشاء **Web App / Node.js**. رفع React إلى `public_html` لا يشغل API.
استخدم Node.js مدعوماً، ومنفذ `PORT` الذي تحدده الاستضافة، واحتفظ بأسرار
البيئة خارج الملفات العامة. لا تغيّر DNS أو تنقل `takyeh.sa` قبل اجتياز
اختبارات النسخة الجديدة.
