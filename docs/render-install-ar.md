# تشغيل تكيّة على Render من GitHub

أنشئ **Web Service** باستخدام مستودع `hekayatanaqah-code/takyeh` وفرع `main`.
لا تستخدم Static Site؛ تسجيل الدخول والحجوزات والمدفوعات تحتاج خادم Node.js.

- Root Directory: اتركه فارغاً (جذر المستودع).
- Node.js: ‏24 عبر `NODE_VERSION=24`.
- Build Command: ‏`corepack enable && pnpm install --frozen-lockfile --prod=false && pnpm run build:cloud`
- Start Command: ‏`pnpm start`
- Health Check Path: ‏`/readyz` (جاهزية تهيئة التطبيق، وليس فحصاً دورياً لاتصال القاعدة).

لا تضع PORT ثابتاً؛ Render يزوده تلقائياً. `server.cjs` يستمع على `0.0.0.0`
ويقرأ `process.env.PORT`، ويستخدم 3000 للتشغيل المحلي فقط عند غيابه.
البناء ينتج الواجهة والخادم من المصدر؛ لا يعتمد على ZIP أو generated-artifacts
أو إعدادات Hostinger. أمر `pnpm run build:cloud` ينتج الواجهة مباشرة داخل
`dist` في جذر المستودع، ويقرأ الخادم `dist/index.html` وملفات `dist/assets`.
تعمل روابط الصفحات الداخلية عبر الرجوع إلى `dist/index.html`، بينما الملفات
غير الموجودة ترجع 404 بدلاً من محتوى HTML. لا تستخدم مجلد `public` القديم.
اترك `FRONTEND_DIST_DIR` غير مضبوط لاستخدام `dist`؛ إذا كانت له قيمة قديمة
في Render فاحذفها أو غيّرها إلى `dist`.

## السماح بسكريبتات تثبيت الاعتمادات

المستودع يحدد إصدار `pnpm@10.26.1` لتوحيد التثبيت محلياً وعلى Render.
قائمة `onlyBuiltDependencies` في `pnpm-workspace.yaml` تسمح بسكريبتات
الحزم المعتمدة، ومنها `esbuild` و`ffmpeg-static` و`sharp` و`core-js`،
مع تفعيل السكريبتات في `.npmrc`. لا تستخدم `pnpm approve-builds`
التفاعلي ضمن البناء، ولا تسمح عشوائياً بجميع سكريبتات الحزم.
إذا ضُبط `NPM_CONFIG_IGNORE_SCRIPTS=true` على الاستضافة، احذفه حتى
لا يتجاوز إعدادات المشروع. عند إضافة حزمة جديدة تحتاج سكريبت تثبيت،
راجعها وأضف اسمها صراحةً إلى قائمة السماح.

## البيئة والبيانات

بناء Render يستخدم PostgreSQL الحالية عبر `DATABASE_URL` بموافقة المالك.
لا توجد عملية تحويل أو نسخ بيانات أو إنشاء حسابات أو إعادة إدخال بيانات.
يظل تصدير Hostinger باستخدام `--hostinger` هدف MariaDB مستقلاً.
التخزين المحلي الخاص ما زال يحتاج قرصاً دائماً؛ تغيير محرك الاتصال لا ينقل الصور.

تنبيه: رابط قاعدة تطوير Replit الداخلي ليس عنوان اتصال عاماً لـ Render.
إذا كان الرابط داخلياً، يلزم نقل نسخة PostgreSQL إلى مزود قابل للوصول من
Render بعد اعتماد خطة النقل والتكلفة. لا تنسخ عنواناً داخلياً أو تستبدله
بـ localhost، ولا تفتح قاعدة التطوير للإنترنت لتجاوز هذا القيد.

اضبط بأمان في إعدادات خدمة Render:
- `NODE_ENV=production`
- `DATABASE_URL`: رابط PostgreSQL الحالية بصيغة postgresql:// أو postgres://، مع السماح باتصال Render وإعداد TLS الملائم لمزود القاعدة.
- `SESSION_SECRET`: سر ثابت بطول 32 حرفاً على الأقل.
- `APP_STORAGE_DIR`: مسار مطلق خاص على **قرص دائم** خارج المستودع ومجلد الواجهة.
- `PUBLIC_SITE_URL` و`PUBLIC_URL` و`PASSWORD_RESET_PUBLIC_URL`: أصل HTTPS الفعلي للخدمة أو الدومين المرتبط.
- إعدادات مزود الدفع والبريد الحاليين عند الحاجة، دون وضع الأسرار في المستودع.

يجب أن تكون PostgreSQL الحالية قابلة للوصول، مع الملفات الدائمة المنقولة وصلاحياتها.
لا تشغّل seed عند تحديث الاستضافة. إذا لم تتوفر قاعدة صالحة أو تخزين دائم،
فتح الواجهة لا يعني جاهزية وظائف المنصة.

بعد البناء، شغّل `node --test scripts/cloud-build-contract.test.mjs` للتحقق
من أن الحزمة اختارت موصل PostgreSQL وأقفالها ولم تخلطها بتنفيذ MariaDB.
الرمز `CLOUD_STORAGE_NOT_READY` يعني أن فحص القاعدة اجتاز مرحلة الاتصال
ثم فشلت تهيئة مجلد التخزين؛ لا تستبدله بمجلد مؤقت لتجاوز فحص الجاهزية.

افحص `/healthz` لاستجابة الخادم و`/readyz` لاكتمال التهيئة، ثم دخول الإدارة
والحجوزات ورفع الصور. تأكد من بقاء صورة بعد إعادة تشغيل الخدمة قبل اعتمادها.
المنصة التي لا توفر قرصاً دائماً ليست مناسبة لملفات الرفع المحلية الحالية.
لا تبدأ نسختين تكتبان إلى قاعدة قديمة وجديدة خلال التحويل.
